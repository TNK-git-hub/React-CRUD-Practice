# CLAUDE.md — AI-native-practice

Spec harness following Spec-Driven Development (Spec Kit, level 4), not yet bound to any app.
This is the **SPEC harness**: it goes from requirement documents to an approved spec, plan and tasks, then hands off
(see "Handoff"). It writes no code and no tests. A separate CODE harness and TEST harness do that (not built yet).
The spec is the source of truth; code and tests must trace back to the spec through IDs.
When there is an app: put the requirement documents in `docs/requirements/`, run `/spec-bootstrap`, then work through the changes in `specs/_system/roadmap.md` one by one.

## Branches

- The main branch is `new-project` (do NOT use `main`). Every PR targets `new-project`; every diff comparison uses `new-project` as the base.
- Harness setup: branch `harness/<task>` (e.g. `harness/day1-init`).
- Feature change: branch `NNN-<name>`, created automatically by `/speckit-specify`. Never name a branch `NNN-...` for anything else.

## Directory layout

```

  agents/                   spec-writer.md, planner.md
  hooks/                    allow_paths.py (blocks writes outside allowed directories)
  settings.json             shared permissions
.specify/
  memory/constitution.md    project principles
  templates/overrides/      customised templates (spec-template.md = delta template, capability-template.md = living spec template,
                            plan-template.md = adds mandatory ## Test Strategy,
                            tasks-template.md = no test tasks, every task lists its scenario IDs)
  presets/                  installed presets (speckit-level4)
  scripts/                  next_change.py, spec_check.py + Spec Kit core scripts
tools/speckit-level4/       local preset replacing the speckit.specify command
.github/                    workflows/ci.yml (required checks: test, spec-check), pull_request_template.md
docs/requirements/          source requirement documents (BA, customer)
specs/
  _system/                  edge-case-catalog.md (shared); glossary.md, domain-model.md, nfr.md, roadmap.md, traceability.md (created per app by spec-bootstrap)
  capabilities/<domain>/    LIVING SPEC: spec.md, states.md, rules.md, history.md
  changes/NNN-<name>/       CHANGE IN PROGRESS: spec.md (kind: delta), plan.md, research.md, data-model.md, quickstart.md, tasks.md, checklists/, contracts/

```

Two kinds of `spec.md`, told apart by location:
- `specs/capabilities/<domain>/spec.md`: what the system DOES now. Never contains the words ADDED/MODIFIED/REMOVED.
- `specs/changes/NNN-<name>/spec.md`: what this change adds/modifies/removes. Has frontmatter `kind: delta`, `capabilities: [...]`, `primary`, `status`; content is split into `### <domain>` sections under `## Requirements`, and each requirement is marked `ADDED` / `MODIFIED <ID>` / `REMOVED <ID>`.

## ID conventions

- Requirement: `<CODE>-<NNN>`, e.g. `ABC-003`.
- Scenario: `<CODE>-<NNN>-S<n>`, e.g. `ABC-003-S2`, in Given / When / Then form.
- Domain codes: none yet. `/spec-bootstrap` fills the table below once requirement documents exist; a new domain must be in the table before it is used.

| Code | Domain |
| --- | --- |
| _(none yet)_ | |

- An ID that was removed (recorded in `history.md`) is never reissued.
- The name (or description) of every test starts with its scenario ID, e.g. `ABC-003-S2 ...`, whatever the test framework.

## Flow of one change

1. `/speckit-specify` → creates `specs/changes/NNN-<name>/spec.md`. Before writing: read `specs/_system/*` and the related `capabilities/<domain>/`.
2. `/speckit-clarify` → always run in the main session (a subagent cannot ask the user).
3. `/spec-edge-cases` → walks `edge-case-catalog.md`, adds scenarios with IDs and P1–P3 to `spec.md`; writes `checklists/edge-cases.md`.
4. **STOP — wait for the user to approve the spec.**
5. `/speckit-plan` → `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`. `plan.md` follows
   `.specify/templates/overrides/plan-template.md` and MUST fill in `## Test Strategy` (runner and commands, environment,
   naming, test level per scenario type, data safety).
6. `/speckit-checklist` → `checklists/quality.md`. The default checklist name is `quality.md`; never write to
   `checklists/edge-cases.md` (it belongs to `/spec-edge-cases`).
7. `/speckit-tasks` → `tasks.md` from `.specify/templates/overrides/tasks-template.md`: no test tasks, every task lists
   `Scenarios: <ID,…>`, every scenario of `spec.md` belongs to at least one task.
8. `/speckit-analyze` → fix CRITICAL findings in plan / tasks (spec problems: stop and report).
9. **STOP — wait for the user to approve plan and tasks.**
10. **HANDOFF** (see "Handoff"): commit the change folder on branch `NNN-<name>`. Do not open the PR yet:
    `spec-check` fails until the change is archived.

Do not use `specify workflow run speckit`: the core workflow still has an implement step.

After the handoff (other harnesses, not this one): CODE harness → TEST harness → `/spec-archive <change>` in the
main session (merges into `capabilities/`, moves the change to `archive/`) → PR into `new-project` →
CI (`test` + `spec-check`, required) → review → merge. Gate run locally first:
`python3 .specify/scripts/spec_check.py --change <change>`.

## Handoff

The SPEC harness ends at step 10. What each downstream harness reads from `specs/changes/NNN-<name>/`:

| Harness | Reads |
| --- | --- |
| CODE | `tasks.md`, `plan.md`, `data-model.md`, `contracts/`, `quickstart.md` |
| TEST | `spec.md`, `checklists/edge-cases.md`, the `## Test Strategy` section of `plan.md` |

Neither downstream harness edits `spec.md`; a spec problem found downstream comes back to this harness as a new
clarify / spec round. `/spec-archive` runs only after the CODE and TEST harnesses are done.

## Hard rules

- Only `spec-archive` may modify `specs/capabilities/`.
- Spec wrong or incomplete during plan / tasks: stop and report; never edit the spec to match the plan.
- Red test: fix the code, never edit the test to make it green.
- Never invent limits, numbers or permissions: mark unclear points `[NEEDS CLARIFICATION]`.
- Delete data exactly as the policy in `specs/_system/nfr.md` says; no policy yet → write `[NEEDS CLARIFICATION]`, do not pick one.
- The stack is chosen by the `plan.md` of the first change; always enable that stack's strictest type-checking mode.
- Never `git push` on the user's behalf; never push directly to `new-project`.
- Never hand-edit `.claude/skills/speckit-*` or core templates: put changes in `tools/speckit-level4/` or `.specify/templates/overrides/`.

## Harness status

Being set up following a 7-day roadmap. If a skill or file mentioned above does not exist yet, tell the user; do not create it in its place.

This harness deliberately has no `speckit-implement`, `speckit-converge` or `speckit-taskstoissues` skill and no
`implementer` agent. Upgrading Spec Kit (`specify init` / `specify integration` …) can regenerate those skills: delete
them again (and their entries in `.specify/integrations/claude.manifest.json`) after every upgrade.

## Machine setup

- Python 3.9+ with PyYAML (`python3 -m pip install --user pyyaml`). Once a preset is installed,
  Spec Kit's template resolver parses `preset.yml` with Python; without PyYAML every command that
  resolves a template (`/speckit-specify`, `/speckit-plan`, `/speckit-tasks`, `/speckit-constitution`) fails.

## Language

- All files are written in English: harness files (skills, templates, constitution, catalog, scripts),
  `docs/requirements/`, `specs/_system/`, `specs/capabilities/` and `specs/changes/` (spec, plan, research, tasks,
  checklists). Requirement sentences read "The system MUST …".
- Requirement sources in another language are translated to English before they go into `docs/requirements/`.
- Exception: user-facing text of the product (UI labels, messages, emails) is quoted verbatim in the product's
  language, in double quotes, so tests can match it exactly.
- Structure stays exactly as in the templates, because scripts and core Spec Kit commands parse it: headings
  (`Overview`, `Requirements`, `Success Criteria`, `Assumptions`, `Out of Scope`, `Merged changes`, `Removed IDs`, …),
  labels (`**Permissions:**`, `**Scenarios:**`, `**Reason:**`, `**Migration:**`, `**From:**`, `**To:**`,
  `**Replaced by:**`, `**Source:**`, `→ Recovery:`), delta keywords (`ADDED`, `MODIFIED`, `REMOVED`, `RENAMED`),
  `Given` / `When` / `Then`, scenario types, `P1`–`P3`, frontmatter keys and the marker `[NEEDS CLARIFICATION: …]`.
- IDs, file / folder / branch / change names, variable names, code and commit messages are in English.
- Reply to the user in the language they write in.
