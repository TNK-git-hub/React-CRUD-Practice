# Decisions for the demo (2026-11-17)

Answers to the open questions raised by `/spec-bootstrap`. The user delegated these decisions ("decide them
yourself"); they are demo choices, not answers from ValueMax, and can be changed through a later change.

**2026-11-18:** the user answered Q1–Q9 of `docs/claude-code-demo/GAP_REPORT.md`. Rows marked *Changed* or *Clarified*
keep the previous decision in italics; D-33 to D-47 are new.
"Brief" = `docs/requirements/singpass-demo-brief.md`.

| ID | Question | Decision |
| --- | --- | --- |
| D-01 | Realtime limit to assert in tests (NFR-001 "about 1 second") | **Changed 2026-11-18 (Q4).** The system learns about consent only by polling the gateway (no webhook). The auto-verify job runs every `POLL_INTERVAL_MS`, default **2 seconds** (configurable); Demo Control has a **"Run job now"** button. Once a job run changes a party, the event reaches connected dealer / Ops clients through SSE without a reload. Tests assert the job result and the event, not wall-clock latency. *Was: ≤ 2 s from the customer's Submit to the client.* Reason: the real ValueMax gateway does not call back, so the delay is the poll interval plus SSE |
| D-02 | Demo Control reset: delete type | Hard delete of applications, parties, verification links and Myinfo records; nothing is kept and nothing can be restored. The sample dealers, users and test personas are not deleted (they are re-created if missing) |
| D-03 | Encryption of Myinfo data (NFR-012) | AES-256-GCM; the key comes from the backend environment variable `MYINFO_ENCRYPTION_KEY` (never committed); the backend refuses to start without it. **Clarified 2026-11-18:** there is no default key; a missing key and a key that is not 64 hexadecimal characters each stop the server with a clear message (tested by starting the server) |
| D-04 | May a dealer user resend the Singpass email? | **Changed 2026-11-18 (Q2).** Yes: Ops, and the dealer agent who submitted the application (Proposal §3.1). A reason is required; limit in D-39. Customers cannot resend. *Was: only Ops.* Reason: the proposal gives the submitting agent the resend action; the dealer is the one in contact with the customer |
| D-05 | Who may use Demo Control? | Any signed-in user (dealer user or Ops); the backend refuses Demo Control calls without a signed-in session. Customers (link holders) cannot |
| D-06 | Time zone | Times are stored in UTC and shown in Singapore time (Asia/Singapore, UTC+8) in the design's format `DD-MM-YYYY HH:mm` |
| D-07 | Measurable "smooth, stable" demo (NFR-030) | No extra number: the 5-minute demo script of the README runs end to end after a reset without an error |
| D-08 | Sign-in method and session | Role switch without a password: the sign-in page offers "Alex Tan — Demo Motors Pte Ltd" (dealer) and "Priya Nair — VMAF Ops" (Ops); the session is a server-side session cookie that lasts until sign-out or the browser is closed |
| D-09 | Dealer sees only own dealer's applications | Yes (prototype fig. 5.1). A second sample dealer, "Sample Auto Pte Ltd", exists only to own sample applications for the Ops list |
| D-10 | "Mandatory documents accepted" and "FI Review completed" in "Cannot issue AA yet" | Not shown: documents and FI Review are out of scope; the box lists only the Singpass condition of each party |
| D-11 | Can the AA be issued without an IPA? | Yes; the only AA condition is that every party's current link is FULFILLED. **Clarified 2026-11-18:** the IPA can be issued by Ops at any time after submission whatever the Singpass status, once. The AA check is a list of conditions (`server/verification/approval.ts`) so that documents, open queries or a second approver can be added once ValueMax confirms them; none is added now. A refused AA returns every missing party with its status and is audited (`aa.refused`); Ops see the same check on the details page. No setting turns the check off. A party whose NRIC is corrected after an IPA keeps the IPA; the AA is locked again until that party is FULFILLED |
| D-12 | Accepted NRIC/FIN prefixes | S, T (NRIC), F, G (FIN), M (FIN from 2022), each with its official checksum letter; input is trimmed and upper-cased before validation. **Clarified 2026-11-18:** checksum = Σ digit × (2, 7, 6, 5, 4, 3, 2) + offset (S/F 0, T/G 4, M 3), then the letter at index (sum mod 11) of `JZIHGFEDCBA` (S, T), `XWUTRQPNMLK` (F, G) or `XWUTRQPNJLK` (M). All 9 test personas, including `M5004553J`, pass |
| D-13 | Mobile number | Exactly 8 digits, starting with 8 or 9. **Changed 2026-11-18 (Q5):** used for a simulated SMS (outbox only, no real SMS) that says the verification email was sent; the SMS **never contains the link**. *Was: stored only, no SMS.* Reason: the required flow sends email + SMS; QnA A3.5 keeps SMS as a notice only |
| D-14 | When does "Credit Review" change on the tracker? | Derived, no Ops action: it becomes current when every party is Fulfilled and no IPA / AA is issued yet; it is shown done once an IPA or an AA is issued |
| D-15 | Is "Pending Singpass Verification" a state of its own? | No: it is derived — current while any party is not Fulfilled, done when every party is Fulfilled |
| D-16 | Retry after "NRIC mismatch" or "Declined" on the same link | **Changed 2026-11-18 (Q1).** There is no "Declined" status (D-33). After NRIC mismatch the link is used up; the customer needs a new link (resend, or Ops corrects the NRIC, D-40). *Was: the same for Declined.* |
| D-17 | Reopening a Fulfilled link | Shows "This link is no longer valid" like every used, expired or superseded link |
| D-18 | Resend after Fulfilled | Not allowed: the button is disabled and the server refuses it. **2026-11-18:** also refused for every party once the AA is issued |
| D-19 | Resend of an expired link | Allowed; the old link stays "Expired". **Clarified 2026-11-18:** issuing a new link (submit, resend, NRIC correction) turns every still-active link of the party (QUEUED, SENT, OPENED) into REPLACED; EXPIRED and MISMATCH links keep their status as history (D-20). The party's current link is an explicit pointer (`currentLinkId`), never derived from link statuses: data arriving on, or a portal visit to, a link that is not the current one is rejected whatever that link's status |
| D-20 | Expiry of a used link (mismatch / declined / fulfilled) | No change: a link that already has an outcome keeps it after 72 hours |
| D-21 | NRIC comparison | Case-insensitive, after trimming spaces on both sides |
| D-22 | Data of an "NRIC mismatch" result | Only the returned `uinfin` is kept (shown red to Ops next to the dealer-entered NRIC); the rest of the Myinfo data is discarded |
| D-23 | Customer submits through a link that was replaced or expired | **Changed 2026-11-18.** The simulated gateway accepts consent on any LinkId it issued (the real gateway cannot cancel a link), so the phone shows "Details shared". When the job or "Retrieve MyInfo" fetches that data, AutoFinance rejects it: it is not attached, the party status does not change, only an audit event (\"result rejected — old link\") is recorded and shown to Ops in the activity log of the application details page. *Was: rejected at submit; the phone shows "This link is no longer valid".* Reason: the gateway is a separate system and AutoFinance only learns about consent by polling |
| D-24 | When is the gateway `LinkId` created? | **Changed 2026-11-18 (Q3).** When the dealer submits (and on every resend / NRIC correction): the adapter's `issueLink` (GetToken + GetLinkId inside) runs, then the email and SMS are sent and the link is SENT. If the gateway is unavailable the submit still succeeds and the link stays **QUEUED**; the job issues and sends it when the gateway is back, never twice. The 72-hour validity counts from the moment the link is actually sent. *Was: when the customer taps "Retrieve Myinfo with Singpass".* Reason: required flow item 3 (QUEUED) and the proposal's link flowchart |
| D-25 | Ops list status labels vs the dealer tracker | Same lifecycle, other labels: "Pending" (submitted, Singpass not complete), "Credit Review" (every party Fulfilled, nothing issued), "Approved — IPA", "Approved — AA". "Declined" appears only on sample data (Decline is out of scope) |
| D-26 | Application Ref numbering | `VMAF-<YYYY>-<NNNNN>`: year of submission and a 5-digit running number, next = max(highest existing, `05120`) + 1, so the first is `05121` and sample refs below it never lower the number |
| D-27 | LTA Access Code | Required, trimmed, non-empty; no format check (no LTA lookup in the demo) |
| D-28 | Same NRIC / email for hirer and guarantor | The guarantor's NRIC must differ from the hirer's; the same email is allowed (handy for a live demo with one phone) |
| D-29 | Sample applications of Demo Control | "Create sample applications" adds the rows of the Ops list design (`VMAF-2026-05114` to `VMAF-2026-05119`) with their dealers, parties and statuses; it skips a reference that already exists. **Changed 2026-11-18:** the guarantor of `VMAF-2026-05118` is EXPIRED instead of Declined (D-33), and every sample person is a Singpass test persona (name and NRIC from brief §6), so no other NRIC appears in sample data and the stored Myinfo data matches the person. *Was: the design's names with made-up NRICs* |
| D-30 | Channel: email vs Singpass app | Email (brief §11) |
| D-31 | Customer review screen before Submit | Shown by default; turned off with the backend setting `MYINFO_SHOW_REVIEW=false` (then "I Agree" submits directly) |
| D-32 | Real gateway spec | Still waiting for ValueMax (B1.1); the demo uses the mock behind an adapter |
| D-33 | Customer declines consent (Q1, 2026-11-18) | No "Declined" status. The real gateway does not report a refusal, so AutoFinance cannot tell it from "not done yet": the link keeps its status until it expires (72 h). The simulated gateway records the refusal on its own side (server log + Demo Control "Gateway log") so the presenter can explain it; AutoFinance never reads it |
| D-34 | MockPass (Q6, 2026-11-18) | Removed (`server/gateway/mockpass.ts`, its test and the `@opengovsg/mockpass` dependency). The only gateway is the built-in simulated ValueMax gateway behind the adapter; `ValueMaxGatewayAdapter` is a stub with TODOs |
| D-35 | Lint (Q7, 2026-11-18) | ESLint with a minimal flat config (recommended JS + typescript-eslint recommended), `npm run lint` |
| D-36 | End-to-end test (Q8, 2026-11-18) | Playwright, one e2e test for the main demo script (submit → open both links from the outbox → consent with the right personas → statuses change by themselves → AA unlocks). Every other SC is tested at service / API level with `node:test` |
| D-37 | Stack (confirmed 2026-11-18) | Keep the current stack: Node `http` server, JSON-file persistence, vanilla JS SPA, SSE. The brief's React / SQLite suggestion is not adopted |
| D-38 | Link states and party labels (2026-11-18) | Link: QUEUED, SENT, OPENED, FULFILLED, MISMATCH, EXPIRED, REPLACED; FULFILLED and REPLACED are final. A party's Singpass status is its current link's status. Dealer / Ops labels: QUEUED → "Queued", SENT / OPENED → "Pending" (Ops detail also shows "Opened"), FULFILLED → "Fulfilled", MISMATCH → "NRIC mismatch", EXPIRED → "Expired" |
| D-39 | Resend limit (2026-11-18) | At most `RESEND_LIMIT` (default 3) resends per party in any sliding window of `RESEND_WINDOW_HOURS` (default 24), measured with the injected clock: a resend at time t counts while now − t < 24 h, so a resend is allowed again exactly 24 h after the oldest counted one. The refusal (HTTP 429) returns that earliest time (`retryAt`) and shows it in SGT. Refused when the party is FULFILLED (D-18). Corrections (D-40) do not count |
| D-40 | Correcting a party's NRIC or email (2026-11-18) | Only Ops; a reason is required; audited (`party.corrected`, old and new values masked). The NRIC must be valid and differ from the other parties' (D-28); something must change. **NRIC corrected, or email corrected while the party is not FULFILLED:** the current link stops being current (QUEUED / SENT / OPENED → REPLACED; a FULFILLED or MISMATCH link keeps its status as history, since FULFILLED is final and D-19 keeps MISMATCH), the previous result no longer counts (Myinfo data, fulfilled date and mismatch NRIC are cleared), a new link is issued for the new details and the party waits for verification again. **Email corrected while the party is FULFILLED:** only the email changes (audited); the result stays valid and no link is issued. Not a resend: it does not count towards D-39. Refused once the AA is issued |
| D-41 | NRIC display and logs (2026-11-18) | NRICs are masked in lists and details (e.g. `S****249H`); showing the full value needs a click and writes an audit event. Server logs never contain a full NRIC or person data |
| D-42 | Time and configuration (2026-11-18) | All time comes from an injected clock (Demo Control can move it forward). `LINK_TTL_HOURS`, `POLL_INTERVAL_MS`, `RESEND_LIMIT`, `RESEND_WINDOW_HOURS` are configuration; the code never detects a test environment |
| D-43 | Old rule tests (Q9, 2026-11-18) | `tests/rules.test.ts` checks the previous behaviour (Declined, Superseded, Rejected): it is replaced by the SC-xx tests. The NRIC / FIN, mobile number and application-ref tests are kept because those rules still hold |
| D-44 | Auto-verify job: data vs expiry in the same cycle (2026-11-18) | For the party's current link while it is SENT / OPENED, the job (and "Retrieve MyInfo") calls `fetchPerson` first and only then looks at the expiry: data → processed (FULFILLED / MISMATCH) even if the link expired during that cycle; no data and past `expiresAt` → EXPIRED. If the gateway is unavailable nothing changes (retried next cycle). Opening an expired link on the portal is blocked but does not itself set EXPIRED: only the job does, after checking for data. Once a link is EXPIRED or REPLACED in the database, any data that shows up for it later is rejected (D-45) |
| D-45 | Late data on old links (2026-11-18) | The job polls the current link only while it is SENT / OPENED, never QUEUED, FULFILLED or MISMATCH links. A separate pass of the same job checks REPLACED / EXPIRED links that have a LinkId, until their original expiry + `LINK_TTL_HOURS`: when data is found it records exactly one `result.rejected` audit event (reason "old link" or "expired", returned NRIC masked, whether it matches) and stops checking that link. This pass never changes a link or party status and never stores the person data. MISMATCH history links are not re-checked |
| D-46 | Resend or correction while the gateway is down (2026-11-18) | The old link becomes REPLACED immediately (the portal blocks it at once); the new link is QUEUED and the job issues and sends it once the gateway is back, exactly once (same rule as D-24); its 72 hours count from that moment |
| D-47 | Expired links list (2026-11-18) | Ops get the list of parties whose current link is EXPIRED (oldest first, with the time a resend is next allowed, D-39) and can resend from it. A party leaves the list as soon as a new link is issued |
