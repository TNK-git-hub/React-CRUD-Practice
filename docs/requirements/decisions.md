yourself"); they are demo choices, not answers from ValueMax, and can be changed through a later change.

| D-01 | Realtime limit to assert in tests (NFR-001 "about 1 second") | **Changed 2026-11-18 (Q4).** The system learns about consent only by polling the gateway (no webhook). The auto-verify job runs every `POLL_INTERVAL_MS`, default **2 seconds** (configurable); Demo Control has a **"Run job now"** button. Once a job run changes a party, the event reaches connected dealer / Ops clients through SSE without a reload. Tests assert the job result and the event, not wall-clock latency. *Was: ≤ 2 s from the customer's Submit to the client.* Reason: the real ValueMax gateway does not call back, so the delay is the poll interval plus SSE |
| D-02 | Demo Control reset: delete type | Hard delete of applications, parties, verification links and Myinfo records; nothing is kept and nothing can be restored. The sample dealers, users and test personas are not deleted (they are re-created if missing) |

| D-44 | Auto-verify job: data vs expiry in the same cycle (2026-11-18) | For the party's current link while it is SENT / OPENED, the job (and "Retrieve MyInfo") calls `fetchPerson` first and only then looks at the expiry: data → processed (FULFILLED / MISMATCH) even if the link expired during that cycle; no data and past `expiresAt` → EXPIRED. | D-45 | Late data on old links (2026-11-18) | The job polls the current link only while it is SENT / OPENED, never QUEUED, FULFILLED or MISMATCH links. This pass never changes a link or party status and never stores the person data. MISMATCH history links are not re-checked |
| D-46 | Resend or correction while the gateway is down (2026-11-18) | The old link becomes REPLACED immediately (the portal blocks it at once); the new link is QUEUED and the job issues and sends it once the gateway is back, exactly once (same rule as D-24); its 72 hours count from that moment |
