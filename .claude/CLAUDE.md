# CLAUDE.md — AI-native-practice

Spec harness following Spec-Driven Development (Spec Kit, level 4), not yet bound to any app.
The spec is the source of truth; code and tests must trace back to the spec through IDs.
When there is an app: put the requirement documents in `docs/requirements/`, run `/spec-bootstrap`, then work through the changes in `specs/_system/roadmap.md` one by one.

## Branches

- The main branch is `new-project` (do NOT use `main`). Every PR targets `new-project`; every diff comparison uses `new-project` as the base.
- Harness setup: branch `harness/<task>` (e.g. `harness/day1-init`).
- Feature change: branch `NNN-<name>`, created automatically by `/speckit-specify`. Never name a branch `NNN-...` for anything else.

## Directory layout

```
.claude/

  skills/                   speckit-* (generated by Spec Kit, DO NOT edit by hand) + spec-bootstrap, spec-edge-cases, spec-archive (our own)
  agents/                   spec-writer.md, planner.md, implementer.md
  hooks/                    allow_paths.py (blocks writes outside allowed directories)
  settings.json             shared permissions
.specify/
  memory/constitution.md    project principles
  templates/overrides/      customised templates (spec-template.md = delta template, capability-template.md = living spec template)
  presets/                  installed presets (speckit-level4)
  scripts/                  next_change.py, spec_check.py + Spec Kit core scripts
tools/speckit-level4/       local preset replacing the speckit.specify command
.github/                    workflows/ci.yml (required checks: test, spec-check), pull_request_template.md
docs/requirements/          source requirement documents (BA, customer)
specs/
  _system/                  edge-case-catalog.md (shared); glossary.md, domain-model.md, nfr.md, roadmap.md, traceability.md (created per app by spec-bootstrap)
  capabilities/<domain>/    LIVING SPEC: spec.md, states.md, rules.md, history.md
  changes/NNN-<name>/       CHANGE IN PROGRESS: spec.md (kind: delta), plan.md, research.md, tasks.md, checklists/, contracts/
  archive/NNN-<name>/       changes already merged into capabilities
tests/<domain>/             tests; each test name starts with a scenario ID
```

Two kinds of `spec.md`, told apart by location:
- `specs/capabilities/<domain>/spec.md`: what the system DOES now. Never contains the words ADDED/MODIFIED/REMOVED.
- `specs/changes/NNN-<name>/spec.md`: what this change adds/modifies/removes. Has frontmatter `kind: delta`, `capabilities: [...]`, `primary`, `status`; content is split into `### <domain>` sections under `## Requirements`, and each requirement is marked `ADDED` / `MODIFIED <ID>` / `REMOVED <ID>`.

## ID conventions

- Requirement: `<CODE>-<NNN>`, e.g. `ABC-003`.
- Scenario: `<CODE>-<NNN>-S<n>`, e.g. `ABC-003-S2`, in Given / When / Then form.
- Domain codes: none yet. `/spec-bootstrap` fills the table below once requirement documents exist; a new domain must be in the table before it is used.

| Code | Domain |
| --- | --- |
| PROD | products |

- An ID that was removed (recorded in `history.md`) is never reissued.
- The name (or description) of every test starts with its scenario ID, e.g. `ABC-003-S2 ...`, whatever the test framework.

## Flow of one change

1. `/speckit-specify` → creates `specs/changes/NNN-<name>/spec.md`. Before writing: read `specs/_system/*` and the related `capabilities/<domain>/`.
2. `/speckit-clarify` → always run in the main session (a subagent cannot ask the user).
3. `/spec-edge-cases` → walks `edge-case-catalog.md`, adds scenarios with IDs and P1–P3 to `spec.md`; writes `checklists/edge-cases.md`.
4. `/speckit-checklist edge cases`
5. **STOP — wait for the user to approve the spec.**
6. `/speckit-plan` → `/speckit-tasks`
7. **STOP — wait for the user to approve plan and tasks.**
8. `/speckit-implement` → `/speckit-converge` until it reports `Converged`; the stack's test suite must be green.
9. `/spec-archive <change>` in the main session → merges into `capabilities/`, moves the change to `archive/`.
10. Two commits (code; spec) → push → PR into `new-project` → CI (`test` + `spec-check`, required) → review → merge.
    Run the gate locally first: `python3 .specify/scripts/spec_check.py --change <change>`.

## Hard rules

- Only `spec-archive` may modify `specs/capabilities/`.
- Spec wrong or incomplete during implementation: stop and report; never edit the spec to match the code.
- Red test: fix the code, never edit the test to make it green.
- Never invent limits, numbers or permissions: mark unclear points `[NEEDS CLARIFICATION]`.
- Delete data exactly as the policy in `specs/_system/nfr.md` says; no policy yet → write `[NEEDS CLARIFICATION]`, do not pick one.
- The stack is chosen by the `plan.md` of the first change; always enable that stack's strictest type-checking mode.
- Never `git push` on the user's behalf; never push directly to `new-project`.
- Never hand-edit `.claude/skills/speckit-*` or core templates: put changes in `tools/speckit-level4/` or `.specify/templates/overrides/`.
